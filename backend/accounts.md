# Account management

Implemented C10, 17 October 2026, following partner PR #14 merged at `fa1c83a`. The owner selected protecting the last **enabled admin who completed password setup**. Newly provisioned restricted admins do not count. This implements account APIs and the admin password-change consumer; a full account-management directory/provision/status UI remains separate frontend work.

## Boundaries and API

The `accounts` module owns account management routes, strict validators, service/repository, safe management DTOs and signed directory cursors. Auth owns password hashing, login/session authorization and credential transitions. The service calls auth's public provisioning helper inside the existing durable command transaction; the helper returns only a user ID. Management reads select explicit safe columns and never load a password hash.

- `GET /api/v1/users`: admin-only list, optional exact `role=admin|partner|driver`, limit 1–100/default 25 and opaque cursor. Includes disabled users. No undocumented search/status filter.
- `GET /api/v1/users/:userId`: safe account identity, including current enabled/restriction metadata and actual membership if present. Absent account returns 404.
- `POST /api/v1/users`: strict admin creation (`role: admin`, email/name/optional phone/initial password). Normalizes email, preserves 15–128-character password bytes, sets enabled and `passwordChangeRequired=true` server-side. Required Idempotency-Key; user, projected audit and safe 201 replay commit atomically. A globally duplicate email returns generic 409 ACCOUNT_CONFLICT without overwrite. No password/hash/token is returned, stored in replay or copied into audit.
- `PATCH /api/v1/users/:userId/status`: strict `isActive` and required 1–500-character audit reason; required Idempotency-Key. Rechecks current authorization for replay, then resolves the original result before new eligibility checks. A new intent updates the flag and atomically revokes all target sessions when disabling, with audit/replay. New no-op intents are audited and disabling an already disabled account still removes any live sessions. Enable never resurrects a revoked session. No undeclared If-Match/version contract.

Only enabled admins with completed password setup can manage accounts. Current partner/driver credentials cannot read account rows/counts or issue management writes. Directory identity is not authentication scope: orphaned partners and future driver-role users can be described safely without being granted sign-in. Driver profile storage/auth is still M3, so driverId is null until that actual relation is implemented. Status does not create/change driver operational eligibility, company state, memberships or history.

## Final-admin safeguard and ordering

A new disable of a currently usable admin requires another enabled admin with `passwordChangeRequired=false`. Otherwise 409 LAST_ACTIVE_ADMIN leaves all rows, sessions, audit and replay unchanged. A restricted account can be disabled without reducing the usable-admin count. Admins may disable themselves when another usable admin remains. Their session is revoked in the same commit, so an old bearer cannot replay a self-disable after a lost response; use another current admin to inspect/manage the account.

Every account-status command takes the same transaction-scoped PostgreSQL advisory lock **before** actor/session row locks, then reauthenticates the actor. Taking the lock afterward would allow two admins to hold opposing actor SHARE locks while trying to disable one another. The global status order makes simultaneous self-disables preserve one usable admin; cross-disables allow one commit and reject the now-disabled opposing actor. Target user locks serialize status with login/password changes; auth login rechecks its verified hash under the user lock, and password changes recheck session/account/hash before commit. Login and refresh cannot bypass current account state.

The reserved two-integer advisory key is `(1213350482, 1)`; it is separate from command-scope bigint locks. Only status changes use this serialization gate, not ordinary reads or company workflows. Existing pool/query/transaction bounds apply. If acquisition fails/times out, the transaction returns sanitized 503 ACCOUNT_CHANGE_RETRY_REQUIRED plus Retry-After: 1; no workflow writes have occurred. Retry explicitly with the same key/body. This is an application API safeguard, not protection against a database operator deliberately issuing direct SQL.

## Directory precision and rollout

User timestamps remain timestamptz(6). Directory queries retain six PostgreSQL fractional digits in their signed anchors rather than round through JavaScript Date; SQL predicates preserve microsecond differences and UUID ties. DTO timestamps remain valid ISO dates, while cursor precision stays internal. Role-filtered totals and page rows share one repeatable-read snapshot; cursors bind current admin, role filter, collection and order. New additive migration `20261017161000_add_user_directory_index` adds the matching `(created_at,id)` index, preserving all existing account/hash/session/history data.

Deploy that migration before the updated API, then coordinate the admin client with CreateUserRequest's 15–128-character initial-password bound. No new dependencies or environment variables. Operational bootstrap remains a separate unique-account command with operator-owned permanent credentials; it cannot update an existing account and does not replace the authenticated management APIs. Preserve additive schema, changed credentials, revocations and append-only history on rollback. The preceding API keeps first-login restrictions but exposes no management routes; its admin client has no password-change screen, so restricted admins need the updated client to complete setup. Do not roll back below PR #14 while restricted admin accounts are enabled: earlier admin APIs do not enforce this flag.

## Admin first-login consumer

The admin portal reads the password restriction from login/refresh and authoritative `/users/me`; restricted admins reach `/change-password` before any business request or workspace shell. The page verifies current/new/matching confirmation, supports password managers/visibility, preserves exact bytes, and honors server throttling. It sends only current/new passwords with browser credentials, CSRF header and Origin; no replay header or automatic retry. Passwords live only in local state/private request refs, never query/mutation variables/results, storage or URL state. Success discards credentials and private caches, clears/broadcasts the local session and requires new sign-in; no old token is promoted after the server clears the flag.

A definitive wrong-password/validation response remains recoverable. An uncertain transport/server/unexpected response locks resubmission and offers sign-out/fresh sign-in with the new password to determine the outcome. No blind credential replay. Unmount/session replacement aborts transport and drops late results; refresh renewal is suspended while the password change is pending and browser cookie operations use the existing shared lock. The partner portal remains a starter template; its first-login screen is still separate.

Validation covers populated upgrades, raw timestamp microseconds, DTO/privacy, scoped cursors/counts, duplicate email/intents, authorized replay, current account/role/session/restriction, all-transport revocation/no resurrection, final usable-admin denial, simultaneous self/cross-disables, bounded mutex contention and rollback after audit/replay failures. Admin unit/mock/live browser suites cover restriction routing, credential cleanup, matching validation, throttling, uncertain outcomes, stale responses and real provision → change → fresh sign-in → disable/enable. Results/PR are tracked in [todo](todo.md) and [verification](README.md#verification). Independent security/shared-contract review and managed/pilot evidence remain separate gates.

Lock ordering and transaction-scoped advisory semantics follow [PostgreSQL 18 explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS). No Redis coordination role is introduced.
