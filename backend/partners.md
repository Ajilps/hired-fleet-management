# Partner accounts and first-login password change

Implemented M2 slice, 17 October 2026. Company/rate PR #13 merged at `1f3f2d2`; this increment completes C07 and the partner portions of C08/C09. The owner selected mandatory password change on first login under DEC-03. Independent security/shared-contract review and partner client screens remain separate work.

## Module boundaries and provisioning

Companies owns membership and its routes/controller/validator/service/repository. It calls the auth module's public account-creation and safe identity functions inside the existing branded workflow transaction. Auth owns password hashing, identity/session checks and credential lifecycle. No new library or Redis dependency is added.

Admin `GET/POST /api/v1/companies/:companyId/partners` are now live. POST accepts normalized email, trimmed name, optional phone, opaque 15–128-character initial password and primary-contact flag. Role, company membership, enabled status and password-change restriction are assigned by the server. A globally conflicting email returns generic 409 `ACCOUNT_CONFLICT`; existing accounts are never overwritten or attached. One partner belongs to exactly one company. Multiple primary contacts are permitted by the existing boolean contract; it does not declare an exclusive primary contact.

Provisioning uses the command coordinator: reauthenticate current admin, authorize the company, resolve the actor/path/key replay, lock the company, create the Argon2id-hashed user plus membership, append a projected audit event and persist the safe 201 result in one commit. Hashing happens only for a new intent inside the bounded transaction and existing four-operation hash limit; replay avoids hashing. Concurrent duplicate keys create one account. Distinct intents with the same normalized email conflict. Membership, audit or replay failure rolls back the entire result. The raw password participates only in the keyed request fingerprint; no raw credential, hash or issued token enters replay/audit responses. Replaying after the partner changes their password returns the original creation DTO, not a current account snapshot.

Lists include enabled and disabled users. Rows use descending membership-created timestamp/user UUID order, a matching index and repeatable-read count/page snapshot. Signed cursors bind actor, company, collection and order. Company status does not disable account provisioning or historical profile access; future order intake must check the company flag.

## Restricted sign-in and change

Login/refresh/current identity now support admins and partners with exactly one stored company membership. Driver integration remains M3. `User.passwordChangeRequired` is explicit public metadata. Newly provisioned partners have it set to true; existing accounts and operational bootstrap admins default false in the additive migration. No bulk credential reset is performed.

A restricted session can read its identity, list/revoke its own sessions, log out, refresh and change its password. All implemented company workflows reject it with `403 PASSWORD_CHANGE_REQUIRED`, regardless of token transport. JWTs contain no trusted company or restriction claim: each protected business request reloads the enabled user, session and membership. Durable commands retain their admin-only default. The company detail read explicitly allows a fully authenticated partner's own company; foreign or unknown company IDs return identical 404 responses. Company lists, rates, partner lists/provisioning and profile/rate writes remain admin-only.

`POST /api/v1/users/me/password` accepts only `currentPassword` and a different `newPassword` of 15–128 characters, preserving spaces with no composition rule. It requires a live bearer session and verifies the current password. Stored browser transport additionally requires the exact allowed Origin and `X-CSRF-Guard: 1`; a caller cannot bypass this by selecting native transport. Durable limits are five attempts/account and thirty/IP per 15 minutes. Hash/verification capacity remains bounded.

After verification/hash work, one transaction locks the user then the current session, rechecks the exact verified hash/session/account, updates the hash and flag, revokes **every** session for the user and appends a credential-free audit record. Failure rolls back all effects. Concurrent changes can commit only once. A login that verified the previous hash cannot create a session after the change. HTTP 204 returns no tokens and clears a browser refresh cookie; sign in again with the new password. Old JWTs/refresh credentials remain invalid after the flag clears. Do not automatically retry or use the durable command registry for this credential transition: revocation intentionally removes the old authorization. After a lost response, attempt a fresh login with the new password; if the old credential still works, it remains restricted and the change can be submitted again.

`b2b-portal` is a Vite starter template with no partner sign-in or password-change screens. Its first-login screen must use the flag/endpoint, keep credentials only in transient state, clear them after completion and require fresh sign-in. The admin portal provisions and lists partners, explains the first-login requirement and refuses partner sign-in. Live browser tests exercise the partner API lifecycle using a separate browser context. Recovery/invitation delivery and initial-credential expiry are not introduced in this slice; operators must share credentials securely, and those lifecycle policies remain release work.

## Migration, verification and rollout

Apply `20261017152000_add_partner_password_lifecycle` before running this API. It adds the non-null default-false user flag and membership pagination index. Readiness probes the flag so an old schema refuses traffic. Deploy the updated API and provisioning client together; older clients must not assume a successful login grants business access when the flag is true. On rollback preserve the schema, hashes, revocations and append-only audit. The preceding merged API supports admins only, so rolling back to it disables partner sign-in while preserving partner data. Any future compatibility rollback must preserve restrictions rather than granting unrestricted access from an initial password.

Synthetic PostgreSQL tests cover populated upgrade/repeated deployment, privacy, duplicate/racing intents, rollback on membership/audit failure, cursor scope/ties/totals, browser/native restriction, password verification/policy/throttling, all-session invalidation, concurrent credential changes, stale verified login, membership changes/removal, disabled users, inactive company history and two-company denial. Live desktop/mobile tests cover real provisioning, reload, first-login change, cookie removal, refresh and admin-role denial; intercepted regressions remain separate evidence. Password verification and post-change session invalidation follow [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#change-password-feature) and [session renewal guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#renew-the-session-id-after-any-privilege-level-change).
