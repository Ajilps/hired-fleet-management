# Orders and accepted-trip handoff

Implemented 22 October 2026 under owner-selected DEC-04/20. Partner/admin intake uses the existing shared session and durable-command boundary. Partners omit company/source; current membership supplies both. Admins supply company and an admin intake source. Unknown fields, unpaired coordinates, invalid dates and malformed exact amounts fail validation. There is no binding partner price. Date filters are inclusive from/exclusive to. Lists use signed actor/company/filter cursors and snapshot totals.

Admin decisions require Idempotency-Key and the strong order ETag from detail. Lock company then order; acceptance/rejection serialize. Acceptance atomically stores one unassigned trip, encrypted code material, order decision, audit, replay and company-contact email intent. Rejection stores reason/actor/time and email intent together. No network email call occurs in this transaction. Current authorization precedes stored replay; moving a partner membership cannot expose an earlier company's create result. Same-command retry returns the original response despite its old precondition. Opposing/new terminal decisions return 409. Any transactional failure rolls back every effect.

Route/contact/schedule and stored estimate evidence copy to the trip. Estimates remain explicitly unavailable until DEC-32 config is selected; supplied distance is preserved. Ordinary DTOs, audit, email payload and command results exclude all code material. Code creation uses uniform six-digit randomness, dedicated AES-GCM trip-bound key material, versioned key IDs and keyed validation hash. Missing cipher config disables acceptance with 503; intake/rejection still work. Reveal, lockout accounting and closure are M5 work, not delivered by material creation.

Host API: set independent TRIP_CODE_ENCRYPTION_KEY (32-byte base64url) and TRIP_CODE_KEY_ID; keep the key stable across restarts. TRIP_CODE_PREVIOUS_KEYS is a JSON map of retained IDs to old keys. Never repurpose an ID. Local Compose generates and persists a separate trip-code-key.json alongside existing local keys. Backup/key recovery remains required before real-data use.

Verification: `node --import tsx --test tests/orders.test.ts`; with TEST_DATABASE_URL pointing to a disposable loopback PostgreSQL with CREATE DATABASE permission, run `node --import tsx --test tests/integration/orders.integration.test.ts`. Tests create/drop their own synthetic databases and exercise actual SQL, HTTP, transactions, races and faults. No customer notifications are sent.

## Trip reads and local email worker

GET /trips and /trips/:id provide the accepted-trip handoff. Partners see only current-company trips. Admins filter company/driver/status/scheduled range and inspect paginated assignment history. M4 creates only unassigned trips; M5 owns assignments, operational transitions and credited-driver closed history. No close-code reveal is exposed in M4.

Run `pnpm run notifications:work` separately with NODE_ENV=development, NOTIFICATION_TRANSPORT=capture and the database URL. Compose starts notification-worker after the API is ready. It writes private complete JSON files under backend/.local-state/mail (inside the persistent local-state volume in Compose), never SMTP/customer email. It rejects capture in production. Stop with SIGTERM/SIGINT. Capture filenames are notification UUIDs; atomic publication and immutable payload checks preserve provider identity after an interrupted acknowledgement.

Claims use FOR UPDATE SKIP LOCKED, 60-second leases and random fencing tokens. Each claim increments the preserved historical attempt count; five attempts per cycle, delays of 1/5/15/60 minutes. Only a current unexpired lease can acknowledge. Provider exceptions persist DELIVERY_FAILED, never exception contents. Exhausted crashed claims become failed. Admin POST /notifications/:id/retry requires an idempotency key and a failed intent with a recipient; starts a new bounded cycle without resetting attempt history or changing recipient/content. Missing-recipient intents remain visible and cannot be retried without a separately designed correction workflow.

GET /notifications, /notifications/:id and /audit-logs are admin-only sanitized operations. Notification reads exclude payloads, provider references and leases. Audit reads expose metadata only; six-digit timestamp anchors and bigint IDs are preserved. Email success means local capture acceptance here; production provider delivery is not implemented. Future providers must preserve idempotency by notification ID or document duplicate-delivery risk.
