# Driver onboarding foundation

Implemented 18 October 2026 following merged local-storage PR #16 (`f7be6fb`). The owner selected **admin-only onboarding with an initial password and mandatory first-login change**. This is account provisioning, not an emailed invitation service. Public self-registration is closed. Driver document/file storage, scanning, activation and availability remain separate work; this increment implements profiles, authentication, reads and the admin provisioning consumer.

## Boundaries and endpoints

The `drivers` module owns routes/controller, strict validation, service/repository, safe profile DTOs and signed cursors. Auth owns hashing and current identity/session authorization; its public provisioning helper receives the existing shared transaction and returns only a user ID. The command foundation commits user, pending profile, minimal audit and safe replay together.

- `POST /api/v1/drivers`: enabled admin with completed password setup; required Idempotency-Key. Accepts email, fullName, required phone, 15–128-character initialPassword and optional dateOfBirth/homeAddress. Email is lowercased; contact/address text is trimmed; password bytes are unchanged. Date must be a real ISO calendar date not later than the current UTC date; no minimum-age policy is introduced. Required name/phone and optional nonempty address reject NUL and obey 150/30/2000-character bounds. Rejects unknown role/scope/status/activation fields.
- Creates an enabled `driver` user with `passwordChangeRequired=true`, one actual driver profile, `pending` operational status, offline state and null activation fields. No token, password or hash is returned. Admins share credentials securely through their agreed channel; the system sends no invitation/email.
- User/profile/audit/replay commit atomically. Duplicate email across any role returns generic 409 ACCOUNT_CONFLICT without overwrite. Same-key replay rechecks current admin authorization and returns the original safe 201/Location before new eligibility checks; changed input conflicts. No If-Match contract. Password changes or later account changes do not rewrite the saved result. Audit records only profile/user IDs, initial status and the restriction flag, excluding address/birth date/contact and credentials. Replay contains the safe original profile, never a credential.
- `GET /api/v1/drivers` and `GET /api/v1/drivers/:driverId`: admin only, including disabled accounts. Strict optional status and exact `isOnline=true|false`, limit 1–100/default 25, opaque cursor. No invented search, calendar or eligibility filter.
- `GET /api/v1/drivers/me`: enabled driver with completed password setup; profile ID derives from the current stored relation, never client input. Pending/inactive/suspended profile states do not themselves disable account sign-in or own onboarding reads. Operational eligibility remains a separate gate for future trip/availability writes.
- `POST /api/v1/driver-applications`: always 403 ADMIN_ONBOARDING_REQUIRED without creating records. Its deprecated contract records the selected admin-only entry method.

Login, refresh, current identity, password change and own-session management support actual driver scope. Orphan driver-role accounts remain denied; the migration does not fabricate profiles for them. Admin-only routes accept only admins, company reads explicitly accept only admins/partners, and own-driver reads explicitly accept only drivers. Expanding identity support does not expand a route's role allowance. Password-restricted drivers can inspect `/users/me`, change their own password and manage their own session; business reads remain denied until setup and fresh sign-in. Password change revokes every old transport/session. Disabling the user through the account API revokes sessions without changing driver status; enable never resurrects credentials or activates a profile.

## Schema, precision and rollout

Additive migration `20261018043000_add_driver_profiles` adds the mapped driver enum/table, unique user relation, activation foreign key/pair constraint and directory indexes. SQL role guards require a driver account for a profile and prevent converting a profiled driver into another role. Account management DTOs now expose the actual driverId when present. Auth identity and directory projections omit hashes; only authentication loads credential material.

Profile/user timestamps remain timestamptz(6). Directory anchors preserve six fractional digits and UUID ties in SQL, bind admin/status/online filters/collection and use one repeatable-read snapshot for count/page. Reusing another actor's cursor or changing filters returns 422. Counts reflect the whole filtered result, including disabled accounts.

Deploy the migration before the API: readiness now requires driver storage, and current auth queries include its relation. Then deploy the updated admin client. No dependencies or environment variables added; SeaweedFS remains ready for the later files module and is not used by profile provisioning. Preserve profiles, changed passwords, revoked sessions and audit/replay on rollback. The preceding API cannot authenticate drivers because it lacks driver scope, but must not be treated as a way to recover/reset a driver password. Do not drop profile data to roll back application code. Existing enabled restricted accounts require clients that implement password setup; actual Flutter screens/device validation remain pending.

## Admin consumer and remaining scope

The Drivers page links to `/drivers/new`. The form uses the existing UI tokens, persistent accessible labels, password-manager support, visibility toggle, validation/first-error focus and 320–1440px layout. It sends only allowed fields, clears credentials on success/cancel/unmount/session loss, invalidates the directory and opens the saved pending profile. Passwords stay in local form state and a private request ref, outside mutation variables/results, caches, storage and URL state. No credentials appear in success navigation.

Throttling honors Retry-After. Uncertain transport/server/in-progress outcomes retain the same intent/key/body for explicit retry with editing locked. Definitive failures permit correction; a new corrected intent gets a new key. Duplicate submits, automatic retries and offline credential queues are disabled. A lazy-loaded creation page keeps the main bundle within its existing warning threshold.

Real directory/profile/provisioning APIs are integrated. Existing document, activation and availability UI remains unavailable against the current backend; it does not receive fabricated empty/clean/active data. D01 file/scanner/access/retention/activation decisions, D02 file/document models, D04–D09 dependent work, partner portal and driver Flutter screens remain pending. Review and managed/pilot validation are separate gates. See [todo](todo.md) and [verification](README.md#verification) for actual results and the PR.
