# HireD backend

Express/TypeScript modular monolith with infrastructure probes and real **admin, company-scoped partner and profile-scoped driver authentication**: operational bootstrap, login, browser-cookie restore/refresh, logout, current identity and own-session management. See [authentication setup/policy](authentication.md). Real admin company/profile and payout-rate APIs now consume the command foundation; see [setup and policy](companies.md). Partner provisioning, mandatory first-login password change and own-company access are implemented; see [partner policy](partners.md). Admin account reads/provisioning/status, last-usable-admin protection and the admin first-login consumer are implemented; see [account policy](accounts.md). Admin-provisioned driver accounts, current profile scope, mandatory password setup and real admin directory/detail are implemented; see [driver policy](drivers.md). Opt-in private driver-document uploads, ClamAV scanning, uploader metadata and durable recovery are implemented; see [file policy](files.md). Document attachment/lists, encrypted full numbers, five-minute private downloads and initial activation are implemented locally; see [document policy](documents.md). Order/trip/financial APIs remain pending. Fast business-screen regressions still use intercepted responses; dedicated live suites verify auth, companies/rates and partner provisioning.

Follow the [development plan](development-plan.md) for milestones/dependencies and the [todo list](todo.md) for implementation tasks, decision gates and completion evidence.

## Local setup

For the simplest local setup, copy the repository root `.env.example` to `.env`, set `LOCAL_ADMIN_PASSWORD` (15–128 characters), then run **`docker compose up --build`** from the root. Open http://localhost:5173 and sign in with `LOCAL_ADMIN_EMAIL` (default `admin@example.com`) and that password. Development Compose handles dependencies, generated keys, migrations and first-admin creation; restarts preserve existing data/accounts. See the [Docker guide](../docs/docker-setup.md). The manual host setup below remains available.

Use Node **26.11.1** (`.node-version`) and pnpm **12.14.0**. Install that exact pnpm version if necessary with `npm install --global pnpm@12.14.0`. This directory owns its manifest and lockfile; there is no root workspace. `pnpm-workspace.yaml` configures this package's reviewed install hooks and release-age exceptions only.

Start PostgreSQL using the root [Docker guide](../docs/docker-setup.md), then run from `backend/`:

```sh
cp -n .env.example .env.dev
pnpm install --frozen-lockfile
pnpm run generate
pnpm run db:validate
pnpm run db:deploy
```

Match database credentials/port to your local Compose environment, generate independent unique `AUTH_SESSION_KEY` and `COMMAND_FINGERPRINT_KEY` values as described in `.env.example`, and configure exact browser origins. Create your admin using the [operational command](authentication.md#setup-and-tests), then run `pnpm run dev`. There is no default/shared password or public admin registration. Ordinary API/production startup does not create accounts or migrate; the explicitly enabled local Compose wrapper performs this development setup. Synthetic test accounts live only in disposable test databases.

The API listens at `http://127.0.0.1:3000` by default:

- `GET /health`: process liveness, independent of PostgreSQL.
- `GET /ready`: 200 after checking the implemented identity/workflow tables and password-lifecycle column, otherwise a sanitized 503. An empty/unmigrated database is not ready.
- Unimplemented routes return the standard JSON 404 envelope. These probes expose no user information.

The API validates environment configuration at startup, including the required authentication key. Exact origins permit credentialed CORS; browser auth independently checks Origin and the custom CSRF header. CORS does not authorize requests. Responses include a server-generated `X-Request-Id`, security headers and `Cache-Control: no-store`. Credentials and database errors are not logged. JSON bodies are limited to 64 KiB.

## Configuration and database lifecycle

`pnpm run dev` and Prisma scripts load `.env.dev` using Node's native environment-file support; already exported environment values take precedence. Integration tests load `.env.test`. The compiled production process loads no local environment file: inject its environment through the deployment system.

| Setting | Purpose |
| --- | --- |
| `NODE_ENV`, `HOST`, `PORT` | Runtime mode/listener; defaults development, loopback and 3000 |
| `DATABASE_URL` | PostgreSQL runtime connection; default `public` schema only |
| `MIGRATION_DATABASE_URL` | Optional privileged connection used exclusively by Prisma CLI |
| `DATABASE_POOL_MAX` | Per-process pool ceiling, default 10, maximum 100 |
| `DATABASE_CONNECT_TIMEOUT_MS` | Connection/queue wait bound, default 2000 ms |
| `DATABASE_QUERY_TIMEOUT_MS` | Client query and PostgreSQL statement timeout, default 3000 ms |
| `CORS_ORIGINS` | Comma-separated HTTP(S) origins; defaults to no allowed browser origins |
| `TEST_DATABASE_URL` | Explicit disposable migrated integration database; never falls back to `DATABASE_URL` |

Use provider-reviewed TLS settings/CA trust for managed PostgreSQL; do not disable certificate verification. Pool sizing, managed provider configuration and production deployment remain open. Redis is not required by this increment and holds no sessions or authoritative data.

`prisma/schema.prisma` and committed migrations own users/sessions plus consumed refresh hashes and durable auth limiter buckets. Command replay and append-only audit are also implemented as the internal [command foundation](commands.md); Companies/memberships/payout-rate history are also implemented with overlap/immutability guards; other business tables in the [DBML](../docs/database/hired.dbml) remain planned. Preserve explicit mappings/native types and custom SQL CHECKs. [Authentication](authentication.md) records normalization, hashing, session/cookie policy, maintenance and upgrade implications.

- `pnpm run generate`: generate `src/generated/prisma/` without a database URL/connection. Generated files are ignored and compiled into `dist/generated/` with the API.
- `pnpm run db:migrate --name <snake_case_description>`: develop a new migration on a disposable local database; inspect SQL before committing.
- `pnpm run db:deploy`: apply committed migrations using the migration connection, falling back to `DATABASE_URL`. Repeated deployment does not recreate data.
- `pnpm run build` then `pnpm run start`: compile and run `dist/index.js`. Generation must run before the first build.

Run release migrations separately before starting the API. Ordinary API/production startup never runs migrations/seeds; local Compose runs committed migrations through its guarded development wrapper. SIGINT/SIGTERM mark readiness unavailable, drain HTTP requests, disconnect Prisma and enforce a ten-second shutdown deadline.
